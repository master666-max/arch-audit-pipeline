# Arch Audit Pipeline

**吃透一个项目的架构：⓪ 快照 → ①-⑥ 理解与审计 → ⑦ 图表 → ⑧ 三文档。让 agent 干这件事从"看发挥"变成"看程序"——每一步有产物、产物有颗粒度、数字有脚本、结论有 file:line，完成率不足 100% 不许交差。**

## 它解决什么问题

把"帮我搞清楚这个项目"扔给一个 agent，大概率撞上三堵墙：

1. **说完就忘。** agent 侃侃而谈"这个项目分层清晰"，没有产物落盘——三个月后你（或下一个 agent）还得从零再来一遍。
2. **干着干着偷懒。** 流程过半开始跳步：图集"下次再补"、文档"限于篇幅"、审计"结论清晰无需展开"——每一步都看着有道理，加起来是一次烂尾。
3. **说得漂亮，查无实据。** "双核零耦合""没有循环依赖"说得斩钉截铁，你问 file:line，它开始绕。

这个 Skill 的对策浓缩成一句话：

> **架构理解是首要目的，审计是给它兜底的质量门——⓪→⑧ 全量做完是默认承诺：每步产物落盘、数字脚本实算、结论附 file:line、完成率 100% 才准收工。**

## 它有什么不一样

- **沙级颗粒度验收。** 产物按最小可验证单元（一条依赖边 / 一行行号 / 一件文件 / 一条断言）验收；手册只界定颗粒度下限，**结构可自由组织，颗粒度不可降**——不给你一份照抄模板的答卷。
- **十锁执行纪律。** 串行门、执行日志即证据（无 log = 未执行）、数字必须脚本实算（判零也要贴检查）、每步验收底线、结束前自查表、产物可读性（不产密码本）、统一产出根、状态机断点续跑、裁定权只在用户。
- **范围框定是程序，不是感觉。** 确定性信号阶梯（git index → 包根 → 索引 → import 闭包 → 连通团）+ `scope-probe` 探测脚本三清单 + **双跑逐字节一致** + 覆盖率双检（反向覆盖 = 0）。
- **完成率硬门 + 断点续跑。** 九步状态表 + 心跳 n/9；中断后从状态表第一个非完成步骤接着干，已完成不重跑；**完成率 <100% 不得标记交付**；范围裁剪必须用户裁定并引用原文。
- **无损三文档（L2/L1/L0）。** 同一份无损信息的三个语言层级：技术版（原文精度）/ 大白话版（教材规格，术语附真实文献出处）/ 草履虫版（超短句极简）——**比喻是翻译层不是过滤层**，信息保真核对表三份各自打勾。
- **图集下探到哪画到哪。** 全局图集（容器/时序/ER/依赖，最小四张）+ **每个下探模块的模块级图集**（架构/依赖/时序/ER 四类，分级覆盖防爆炸，预算 20-35 张）；依赖图一律脚本批量生成，火焰图来自真实 profile——绝不编造。
- **性能剖面是审计链固定环节。** 真实运行核心链路，cProfile 同源数据 → `perf-report.md` + 火焰图 → 性能发现进审计报告 → 三版文档同步；图与数字同源，禁止两套数。
- **降级不降质，升级不跳过。** 依赖缺失按内置降级策略（grep 建边 + 自写 Tarjan/方向矩阵）走完全程；**首选依赖可用时必须真跑**并与降级件交叉验证——不许拿"装了但没跑"当挡箭牌。

## 一个项目从头到尾

| 阶段 | 步骤 | 产出 |
|---|---|---|
| 前置 | ⓪ 项目搜索与快照打包（信号阶梯 S1-S5 + scope-probe + 覆盖率双检） | `0-bundle/` 只读快照 + README-BUNDLE + 探测三清单 |
| 理解与审计 | ① 范围框定 → ② 静态制图 → ③ 分层下钻 → ④ 架构推断+**性能剖面** → ⑤ 架构审计 → ⑥ 事实校验 | `1-scope/` → `6-facts/`（AGENTS / dep-edges / 模块卡 / architecture / perf-report+火焰图 / audit-report / facts-checklist） |
| 产出 | ⑦ 图表产出 → ⑧ 三文档产出 | `7-diagrams/`（全局级+模块级图集）+ `8-documents/`（技术版 / 大白话版 / 草履虫版） |

**⑤ 是独立质量门**：Critical（循环依赖、分层彻底失效、核心扩展点完全未使用）未清零，`architecture.md` 不得标记可交付。**⑥ 反幻觉兜底**：每条断言附 file:line，证伪回写修正后才算交付。

## 核心立场

- **审计是硬性质量门，不是增值项。** 只描述"现状是什么"而不评估"合不合理"的架构图，是无法区分主干和肿瘤的解剖图。
- **首要目的是搞清楚架构。** 衡量标准是"读者能否拿 ⓪→⑧ 产物链独立讲清：系统由什么组成、块与块怎么调、为什么这样设计、哪里有坑"。每一步产物为"被理解"而写，不为过关而写。
- **产物是给人看的，不是密码本。** 脚本逐段注释、数据产物逐字段说明、缩写首现给全称——生成物里不许出现无解释的自造词。
- **术语要有出处。** 大白话版按教材规格写：术语首现附人话解释 + 英文原词 + 真实可核验的文献出处；**禁止编造文献**，拿不准就写"业界通称"。

## 断点续跑协议

流程是一台可恢复的状态机，不是一次性独木桥：

1. 任何一次开工（含新会话）第一动作：读 `pipeline-log.md` 九步状态表；
2. 从第一个非"完成"步骤继续，已完成且产物在档的步骤**禁止重跑**（被 ⑥ 证伪者除外）；
3. 每步落盘即更新状态表 + 心跳 n/9；大步骤细分心跳（⑦ 记 m/图数，⑧ 记 a/8 + b/9 + c/7）；
4. **交付判定三条同时满足**：状态表全部"完成"（out-of-scope 仅限用户明确裁定并引用原文入 log）、自查表全过、完成率 100%。
5. 上下文将尽：落盘当前步产物 → 更新状态表 → 显式宣布暂停点——**禁止用跳步收尾**；降级只作用于工具，永不作用于步骤。

## 快速开始

```bash
# 安装（用户级）
cp -r arch-audit-pipeline ~/.zcode/skills/
# 重启会话后，对 agent 说：
# "用 arch-audit-pipeline 吃透 <项目名> 的架构"
# 或只跑部分：先裁定范围（"本次只做 ⓪①④⑤"），裁定会引用你的原话入 log
```

产出全部收敛在统一产出根 `arch-audit-output/`：

```
arch-audit-output/
├── README.md           # 产物导航与阅读顺序
├── pipeline-log.md     # 执行日志 + 九步状态表
├── 0-bundle/ … 8-documents/   # 每步一个目录，命名 = 步骤号 + 短名
```

## 常见问题

**为什么不直接问 agent"这个项目架构是什么"？** 一次性回答没有产物、没有验收、没有完成率——三个月后信息归零。本流程把"理解"变成一条可复验的产物链。
**审计会不会拖慢理解？** ⑤⑥ 是理解的质量门：没有门的理解会产生自信的错误（假阳性、编造行号、过期图）。实测经验：审计动作抓出过扫描器假阳性（Tunables）、审计自身失实（⑥ 证伪回写）——门是真的在挡东西。
**Windows 环境测不了 Linux 的问题？** 大小写错配三法全在 Windows 原生可做：静态比对（import 书写名 vs 真实文件名）+ `PYTHONCASECHECK=1` 动态复跑 + 对照实验记录；真 Linux（WSL/CI）只是可选后续。
**一次跑得完吗？** 流程是断点续跑的状态机——上下文将尽时落盘 + 宣布暂停点，下次从状态表接着干；⑦ 图集、⑧ 三文档都支持跨轮次增量补齐。
